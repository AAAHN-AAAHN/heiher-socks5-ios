# Independent continuous audio and location services

## Purpose and scope

This feature supplies independent controls for continuous silent audio and coarse location updates. It preserves explicit user intent and makes serialized recovery attempts while the operating system permits execution. Background services are independent of Server Start/Stop, tab visibility and screen locking. Saved On is not a promise of permission, physical rendering, unlimited background execution or server availability.

The standalone root owns one `BackgroundKeepAlive` facade and persists `background.continuousLocation` and `background.silentAudio` through AppStorage, both initially false. Its Server/Background tab choice is not persisted by this feature. Release supplies the choices from its single Settings owner and is responsible for readiness, revision and disk completion ordering. The facade neither reads storage nor calls the Hev server. Original WAV bytes, minimum iOS 17.2, upstream pins, the common XCFramework and native code are unchanged.

## Functional behavior

### Continuous location

One CLLocationManager uses three-kilometer desired accuracy, no distance filter, background updates, a visible indicator and automatic pausing disabled. It is configured before delegate assignment because authorization may be reported immediately. Permission requests are deduplicated and issued only while active. A new When-In-Use session starts in the foreground; an existing session is not repeatedly restarted on lifecycle advice. Always authorization retains its supported startup path.

Undetermined, denied, restricted and unavailable authorization stop obsolete updates or wait without changing saved On. A nonempty update from the current active manager increments Reads and records the callback observation time. Coordinates and location history are discarded. Reads counts callbacks, not individual CLLocation values. Temporary errors remain visible without clearing intent. Off stops updates, detaches the delegate and releases the manager. Stale callbacks cannot restart or update another manager. Count/time remain in memory across Off/On, are not saved, and reset with a new facade.

### Continuous silent audio

One AVAudioPlayer loops the original 844-byte WAV: mono, 8 kHz, signed 16-bit PCM, 400 zero-valued frames and 50 ms duration. The exact canonical header and all-zero PCM are checked before caching immutable Data. `numberOfLoops = -1` remains the playback backend; there is no spare player or added waveform signal. Direct session management uses `.playback`, `.default` and `[.mixWithOthers]`. The two system-alert/route-disconnect preferences are best effort; their rejection alone does not abort playback. No microphone, ducking or forced output route is added.

One control-queue DispatchSourceTimer schedules the earliest health, retry or bounded progress-probe deadline. The health/retry interval remains 0.5 seconds. When the scheduler arms a timer while playback is unhealthy, it requests Dispatch strict scheduling with the existing 1-millisecond leeway. The next scheduling update after accepted healthy playback restores ordinary scheduling. A mode change cancels and replaces the one source while retaining an earlier deadline in the same work context; repeated failures reuse that source, and its monotonic identity rejects callbacks from a replaced source. Neither queue QoS nor the retry interval changes. A first valid inspection that observes stopped playback or changed configuration after accepted healthy playback starts its first recovery immediately; only a completed failed recovery attempt incurs another retry cooldown. A completed failure's retry deadline is measured from actual reply availability; delayed control-queue consumption does not add a second cooldown after that deadline has elapsed. Within the same outstanding-work or waiting context, an earlier armed deadline survives later hints. A completed or replaced operation can legitimately change that context. A healthy player is inspected and reused without repeating category setup or activation. Completed failures retain On and the same finite failure episode; retry count is not capped. Availability advice may expedite once per episode, while an explicit repeated On remains distinct from an automatic hint. Another owner turning Off or unregistering does not erase the surviving owner's retry deadline or blocked-asset state, and does not erase an already queued explicit On. Repeated hints do not start overlapping attempts or postpone an existing deadline.

An observed stopped player is returned as an explicit known failure before reading the session or optional progress values. Unread configuration is not filled with a guessed Boolean. The next serialized recovery obtains its finite execution claim before inspecting the configuration required for safe player reuse. If that inspection finds a changed configuration, it discards the old player and uses the existing reconfiguration/recreation path. A known category mismatch does not read mode or options, and a known mode mismatch does not read options. A configuration failure is returned before optional position, clock, duration, rate or buffer reads. A required platform call that has already entered still keeps the actual operation gate until it returns.

Playing is published after preparation, play success, `isPlaying`, matching session configuration and current cancellation/resource identity agree. That accepted healthy result closes the failure episode and ends its finite claim together. A real failure after this recovery starts a new episode even if it arrives before the next health inspection. Playback position can corroborate reported state, but does not prove physical rendering.

### Recovery and user intent

| Event or condition | Behavior |
| --- | --- |
| Healthy route, rendering, mute or lifecycle advice | Coalesced inspection; reuse a healthy player |
| System interruption, decoder failure, media loss/reset | Sticky resource invalidation; discard stale results and recover serially |
| iOS 27 application-requested deactivation | Inspect reported playback without invalidating a healthy newer player; an observed stop still recovers |
| Positive/unknown resumption or foreground availability | Preserve On; bounded opportunity to retry before a pending deadline |
| Negative resumption advice | Preserve intent and healthy playback without bypassing retry pacing |
| A valid stopped player | Reuse the existing player when configuration remains valid; if post-start verification still reports stopped, recreate on the next paced attempt |
| Invalid player/configuration | Stop/release the old player, retain cached WAV, then recreate/reconfigure |
| Missing or invalid WAV | Visible error, no automatic disk-read loop; explicit intent/availability can retry. Completed aggregate Off closes this blocked episode, so a changed restored On can validate the resource again |
| Explicit Off | Immediately accept cancellation, cancel automatic timers, show stopping while an entered operation remains unfinished |
| Off-On during activation, preparation or release | Retain the actual outstanding operation and mandatory release barrier; activate only after the old release returns |
| Failed owned release while Off | Show the returned error; no automatic Off retry loop; explicit repeated Off can retry |
| An unreturned platform operation | Retain one operation/player and bounded state; keep control/UI responsive; never invent completion |

`setAudio` accepts explicit service intent before publishing the facade value. `syncAudio` ignores identical storage echoes and applies changed nonexplicit values. A completed aggregate Off clears the previous invalid-asset latch only after the actual stop returns. A later changed load/import On therefore receives a fresh attempt without being relabeled as explicit intent. Another owner's Off or unregistration while aggregate intent stays On preserves the existing blocked state. Explicit On, positive availability and media reset also carry a separate monotonic asset-retry identity. The fixed inbox retains the latest identity separately for explicit On and availability. A failed resource read cannot consume a retry accepted after that attempt was admitted. A signal already incorporated by an admitted start cannot be replayed by its delayed control delivery, reopen a blocked asset or erase a completed failure's retry deadline. An older explicit On cannot relabel a newer availability signal and bypass its per-episode budget. If start admission precedes an availability signal's queued drain, that admission consumes the same one-time opportunity. A genuinely new explicit On remains immediately actionable; a new availability signal retains its bounded opportunity. These identities neither cancel healthy playback nor renew the finite claim of a continuously failed episode. Both audio state fields are assigned coherently before observable delivery, with no later write after a synchronous observer can submit a newer Off. The standalone toggle forwards the runtime intent before writing AppStorage. Release must preserve the same ordering when storage blocks, fails or reenters; settings schema/readiness are owned by Settings and Release.

## Implementation and ownership

`BackgroundKeepAlive` is the MainActor facade for location and displayed audio state. Its ObservableObject conformance is explicitly MainActor-isolated, and its publisher uses an explicit Combine import. Each facade registers an audio owner token and asynchronously unregisters on destruction. The process audio service owns cleanup; an orphan view/controller closure never directly deactivates a shared session. Another enabled owner can retain an in-flight activation. The normal root creates one facade and does not tie its lifetime to the removable tab view.

`LoopAudioService` is a checked Sendable immutable handle. Its one private queue owner holds a short control queue and one exclusive I/O queue. The control queue owns the state machine, operation gate, failure episode, timer, monitor and diagnostic ring. The I/O queue alone creates and calls the non-Sendable endpoint. A short lock protects the latest aggregate intent, monotonic owner/revision/stop/resource/asset-retry identifiers, a fixed-bit inbox and publication/timing/receipt values. No AV operation, file access, platform wait, observer callback or dispatch sync executes inside that lock. Every control adoption preserves a pending Off-On stop barrier, including timer and admission paths. Admission also resolves inspection or player reuse against the newly adopted resource epoch, upgrading either to a rebuild when required. A start consumes the pending invalidation under the same short lock only while its On, stop sequence and resource epoch still match. The existing drain remains queued, but cannot replay that consumed invalidation after healthy recovery; a later invalidating event revokes the newly admitted work immediately. An old inspection does not consume the pending invalidation.

`AudioEndpoint` alone owns AVAudioSession/AVAudioPlayer use. All category/preference/session calls, player allocation, prepare/play/stop and property reads occur on its I/O lane. Fresh intent is checked between potentially blocking calls; when an entered call returns after Off, cleanup proceeds at the next safe point. On iOS 27, activate/deactivate completion APIs keep the gate occupied until actual receipt and consumption. Earlier supported systems use the synchronous API on the same I/O lane. An immutable relay carries only operation/generation receipts through fixed slots and one queued I/O drain. Every new playback start receives a checked immutable delegate proxy and a fresh generation, including a start that reuses an existing player. The proxy retains its generation and value relay without retaining or inspecting a player. A delayed callback from a prior playback lifetime cannot invalidate the new lifetime merely because the player object was reused. Stale generations are rejected before they can overwrite a current receipt and are checked again at I/O consumption.

The service registers the explicit 17-name iOS 27 audio/lifecycle notification set once from the root, using NotificationCenter delivery on the posting thread. Repeated view restoration does not register again. Only normalized enum events cross into the mailbox. iOS 27 deactivation context distinguishes application requests from system interruptions; missing or malformed context retains conservative invalidation. An application source does not identify which same-process component requested it, so its hint still checks the player instead of assuming host cooperation. `BackgroundKeepAliveEvents` retains the separate main-run-loop application-active restoration needed by location. Audio delivery does not depend on a removable view or an unbounded main-queue Combine backlog.

### Finite execution claims

The application root explicitly supplies a UIApplication capability; no bundle name or identifier is used to guess execution mode. A recovery episode admits one named finite claim before preparation. The service starts the request from its I/O work, and the application provider calls the thread-safe UIKit begin on that calling lane. A busy main executor does not delay a normal fresh request or its actual-return continuation. Immediately before issue, the lease checks both its own finished state and the service's latest aggregate On and accepted Stop sequence, outside the lease lock; an Off need not wait for the control drain to cancel a queued begin. A resource-epoch change invalidates the old AV operation but preserves that On/Stop recovery episode, so it must not discard the episode's sole protection request. AV preparation still checks the full resource epoch separately. Off-On cancels the old queued claim even when the latest aggregate intent is On. The same outstanding audio work resumes on I/O only after that call returns, or after an Off cancels it before entry. This is a request-return boundary, not a new grant requirement: a general provider can return before its receipt, or return without a receipt, and audio can still proceed. A duplicate start while the first issue is pending is refused without storing another continuation. Healthy playback, Off, invalid assets and expiration finish the claim exactly once. An Off-On barrier ends the old episode before a new recovery episode can request protection. A token received after finish is also ended once. Failed retries do not renew the episode's claim. Denial, expiration, missing receipts and availability notifications do not create a new episode without accepted healthy playback or an explicit Off-On boundary. Repeated actual healthy-to-failed transitions may request one claim per new recovery; they do not retain or renew a failed episode's expired claim. Grant/no-grant and expiration are recorded separately from audio success.

A checked Sendable application holder protects request admission and returned identifiers with a short platform lock. Normal end and expiration perform actual platform end on MainActor, retaining ownership through that external call. No platform call or external callback executes inside the metadata lock. An ordinary expiration with an available platform ID completes the actual `endBackgroundTask` call inside the expiration handler before delivering logical expiration. If platform end reenters expiration, the holder keeps the same claim occupied and reports logical expiration after that existing end call returns. Normal end and expiration consume the same ID once. A monotonically increasing logical request ID prevents an old callback or end from closing a newer request even if UIKit reuses its raw ID; saturation refuses a new request. If expiration arrives before begin returns any ID, the holder records the ended state and delivers logical expiration once immediately. When the ID becomes available, the holder ends it on main before delivering the receipt and audio continuation. A worker can enqueue this single cleanup without blocking for main; this already-expired exceptional path waits for actual cleanup before continuing. It cannot end an ID the platform has not yet returned. No audio, filesystem operation or worker wait is moved onto main.

The general provider end gate retains its separate utility serial queue, so an arbitrary blocked end cannot occupy control or the audio lane. At most one platform token/end job is retained; if that end does not return, later episodes get no grant instead of accumulating more tokens or cleanup jobs. The application adapter reserves at most one main end job for the current logical request. An inline expiration can end that request, but a remaining queued end reservation still blocks replacement claims until consumed. Stale end calls do not enqueue new cleanup jobs. Expiration performs the same actual cleanup inline instead of waiting for the utility queue. Pending receipt/continuation storage is cleared on handoff so a platform-retained old expiration callback does not retain the settled lease. Explicit Off does not introduce a fresh cleanup claim acquisition before stop: a second blocked acquisition would delay the first safe cleanup point. Finishing an existing claim does not cancel AV work or release its operation gate.

The optional extension adapter uses a separate monotonic identity and semaphore for each request. Acquisition and expiration may arrive in either order. A denial that reports only expired=true ends that holder and settles its no-grant receipt, freeing the shared request gate for a later recovery episode. If a grant already arrived, the existing receipt and immutable-request checks discard that extra receipt; delayed grant or expiration callbacks cannot settle or signal a later holder. End, expiration or its finite 25-second holder deadline releases only that holder; it never cancels audio. The current application root does not select or advertise extension capability. A real extension deployment requires platform comparison and an actual root capability before enabling it; unsupported contexts use no grant.

### Concurrency audit boundary

| Declaration | Mutable state and access rule | External exposure |
| --- | --- | --- |
| `LoopAudioService: Sendable` | No mutable state; one immutable private queue-owner handle | Command/reply values, a diagnostic snapshot and forwarding methods; no AV object returned |
| Private `LoopAudioQueueOwner: @unchecked Sendable` | Control-only policy; I/O-only endpoint; short-lock ingress/publication/timing/receipt slots; notification tokens configured once on MainActor and removed at final destruction | The module's sole custom unchecked boundary, confined to an audio-specific private owner with value-only methods |
| Private non-Sendable `AudioEndpoint` | Player/session use, data/generation and plain pending continuation stay on its I/O queue | Only its owner invokes protocol methods on the supplied I/O queue; system closures capture immutable receipts and relay instead of this endpoint |
| Private nonisolated `DelegateProxy: Sendable` | Immutable generation and Sendable event closure; no AV object stored | Nonisolated callback methods submit a generation/decoder value; explicit type isolation prevents the SDK delegate protocol from moving construction onto MainActor |
| Private `LeaseStorage<Value: Sendable>: Sendable` | Immutable checked platform lock: OSAllocatedUnfairLock on Darwin, Synchronization.Mutex on Linux | Sendable value/closure/result access only; platform calls and waits stay outside the accessor |
| Private `ApplicationHolder: Sendable` | Short-lock request, ID and single queued-end reservation; actual end/expiration serialize on MainActor; begin runs on its calling lane | Immutable logical values; known-ID expiration ends inline, and unknown-ID expiration records its state without inventing an ID |

The one private unchecked wrapper owns the actual scheduling and mailbox boundaries. The adapter loses permission to cross queues; a generic unsafe container does not hide its state. The checked Darwin lock is available from iOS 16 and preserves the iOS 17.2 minimum; no unchecked lock API or newer deployment target is used. Strict-concurrency compilation, source confinement checks and actual adapter queue assertions verify the contract.

The pending plain I/O continuation retains the queue owner through its actual operation completion. This lets the final owner's accepted Off finish cleanup even after the last external service handle is released. A matching receipt moves the continuation out and clears its stored slot before invoking it, breaking the in-flight cycle on completion. A never-returning operation retains that one operation instead of creating replacements. The weak callback relay creates no idle owner cycle, and an already queued delegate drain keeps its queued bit when a player generation is invalidated.

## Design rationale and resource cost

One outstanding operation and one owned player prevent a stuck platform call from spawning replacement workers or racing a second activation. Dispatch queues are scheduling lanes, not promises of dedicated permanent threads. The I/O lane uses userInitiated QoS; claim end uses utility. No real-time or userInteractive escalation is used.

The service holds one active timer, at most one finite claim/end job, a 64-entry diagnostic ring, one latest inbox and a bounded progress sample window. The endpoint caches only the original 844-byte resource. Failed attempts do not append a history proportional to elapsed uptime. UI state is delivered only when its values change; repeated healthy hints do not allocate players, reread the asset or continually rewrite session settings. Strict scheduling is limited to unhealthy playback because Dispatch may override timer power-saving behavior. It remains best effort and does not guarantee a wake-up deadline. A continuously failed episode can retain that policy until recovery or Off. Actual scheduling, API work, audio and location still consume energy. Object bounds do not establish minimum CPU, RAM or battery use on a device.

The progress monitor validates finite values, player generation/resource epoch, monotonic host/device times, read brackets, duration/rate and device/host elapsed agreement. Position movement must agree with the device clock within the accepted uncertainty. File-position quantization has its own optional, independently established bound in file seconds; I/O buffer duration does not establish `currentTime` reporting precision. The application supplies no such bound. An unknown bound cannot make stationary reports informative or suspected-stall evidence, even if a caller supplies a true speculative-recovery flag. Actual observed advancement remains diagnostic evidence. A supplied bound contributes separately to uncertainty, and a changed or removed bound clears the previous observation window.

A 50-ms loop can alias under 500-ms sampling. Bounded nonharmonic probes at 0/17/48/91 ms can supply extra evidence, with at most three added samples per window and separated windows. Quantization or uncertainty that covers the observation makes it inconclusive. Two informative suspect windows, a 30-second cooldown and a per-stall budget are required before a certified speculative rebuild. The default certificate remains false; there is no active calibration or inferred physical qualification. Physical false-positive acceptance is still required before enabling that recovery policy. Identical reported clocks/positions cannot distinguish healthy rendering from an opaque renderer stall.

Diagnostics retain one current API-step enum and its entered/returned times, separate from the grouped UI phase and worker queued/entered times. Property getters, configuration setters, file access and player/session operations identify their actual invocation boundary. For asynchronous session APIs, method return and callback availability/consumption are recorded separately; a returned method does not invent its pending callback. The execution-claim step measures the lease request boundary, including an already-expired request's required main cleanup before continuation; it is not a timestamp of actual UIKit API entry. The operation reply retains its own availability and control-consumption times. These are bounded current values, not a growing per-call history. Delayed-stage observations still use 2 seconds for warning and 10 seconds for an unresponsive-operation label. Those values describe an outstanding call; they are not cancellation deadlines, the UI test timeout or authority to release the gate. UInt64 operation, timer, owner, intent and resource identifiers never wrap and reuse identity; saturation refuses further work and exposes a diagnostic rather than launching an ambiguous operation.

## Operation and limitations

On and Off remain independent for audio, location and server. Permission loss, protected data and recovery failures remain visible without silently erasing On. When a system operation is still pending, Off is displayed as stopping/waiting rather than falsely reporting completed release. A returned owned-session release error is shown explicitly.

The primary physical targets are iOS 27 via standalone SideStore installation and separate LiveContainer guest execution modes. A guest may share process/session resources with a host. Direct management cannot prove exclusive host session ownership; no empty host coordinator or bundle heuristic pretends otherwise. Actual host cooperation would require a verified handshake and separate comparison before that capability is advertised.

Suspension and termination prevent timers/callbacks from progressing. No queue or execution claim promises recovery while the process cannot execute or an entered API never returns. Calls, Siri, routes, media-service changes, first unlock, device permissions, long locked-device sessions, real host contention and energy measurements require physical evidence. Simulator IDs, host fixtures and an SDK compile are not substitutes for that evidence.
