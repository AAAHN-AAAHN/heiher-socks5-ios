## 1. The initial port-zero defect is real, but is not the only defect

macOS original-01: unknown client UDP port, UDP ASSOCIATE reply code 1.
macOS patched-01: same request, reply code 0 and a 64-byte echo payload returns.
However, the returned SOCKS5 UDP source address is incorrect.
The original binary also returns the wrong source when a known client port is
supplied (original-02), so the address defect was not introduced by the patch.

## 2. IPv4 reply source corruption on Darwin

Fresh single associations with udp-port 0 and an IPv4 echo server were compared.
The expected echo source was 127.0.0.1:54228 in the macOS binding test.
All four cases below returned the correct application payload.

| bind-address-v4 | SOCKS5 reply source | Correct address |
| --- | --- | --- |
| '0.0.0.0' | [::1:0:0:0]:54228 | No |
| key omitted | 127.0.0.1:54228 | Yes |
| empty string | 127.0.0.1:54228 | Yes |
| '::' | 127.0.0.1:54228 | Yes |

Raw header, default binding:
`0000000400000000000000000001000000000000d3d4`

Raw header, empty binding:
`000000017f000001d3d4`

The same binding variants on Linux all returned the correct source address.

### Independent native C socket probe

An AF_INET6 dual-stack socket sent and received a four-byte IPv4 echo.
The receive address buffer was filled with 0xA5 before recvmsg.

macOS without explicit IPv4-mapped bind:
`family=30 (AF_INET6), name_length=28, actual=::ffff:127.0.0.1`

macOS with bind(::ffff:0.0.0.0):
`family=2 (AF_INET), name_length=16, actual=127.0.0.1`

Incorrectly interpreting the second address as sockaddr_in6 yields
`::a5a5:a5a5:a5a5:a5a5`, including untouched bytes beyond the returned address.
On Linux both cases returned AF_INET6 with a 28-byte mapped IPv4 address.

### Code trace

- hev-socks5-server/src/hev-socks5-session.c applies the configured outgoing bind.
- hev-socks5-core/src/hev-socks5-udp.c, hev_socks5_udp_fwd_b, passes the returned
  source buffer to hev_socks5_addr_from_sockaddr6.
- hev-socks5-core/src/hev-socks5-misc.c, hev_socks5_addr_from_sockaddr6, checks the
  IPv6 mapped-address bits but does not check whether the returned family is AF_INET.
- An IPv4 sockaddr_in is consequently interpreted using the IPv6 structure layout.

This confirms a Darwin reply-address compatibility defect. It does not establish
which layer discards the reply on the user's Windows/iPhone path.

## 3. Shared fixed UDP port and unknown-client-port associations

All associations in each test were opened before the first round of data.
They used the same client IP and different UDP sockets, with unique payloads.

On macOS, patched-09 (four associations, fixed relay port, unknown client ports)
returned success for every handshake, but its first round gave client 0 a payload
that did not match its own request, while clients 1-3 timed out.
Further rounds showed timeouts and mismatches. Closing control connection 0 did
not immediately stop UDP client 0, consistent with incorrect association ownership.
This is not merely a hypothetical malicious-sender scenario.

Patched-08 (four associations, udp-port 0) returned each client's correct payload.
Patched-11 (eight associations, fixed port, known client ports) also returned each
client's correct payload. The separate default-binding source-address defect was
still present in these macOS matrix cases; payload success is not full UDP success.

These tests exercise an initialization race. They do not establish a universal
packet-loss rate or prove that the user's currently configured UDP port is fixed.

## 4. Separate size limit

With an IPv4 SOCKS5 UDP header, payloads through 1490 bytes returned unchanged;
1491, 1500 and 2048-byte test payloads returned only 1490 bytes.
The address defect also occurs on tiny packets, so enlarging a buffer is not a
correction for that defect. No MTU or buffer patch was applied.

## Device-side isolation without another IPA

On the existing patched IPA, first clear Bind IPv4 Address and restart the server.
Keep the TCP Listen Port unchanged. Separately test UDP Listen Port = 0, leaving
UDP Listen Address empty, to avoid sharing a fixed port between unknown peers.
These are configuration workarounds to test on the iPhone, not a completed engine
fix or a verified end-to-end Moonlight result. The previous port-zero guard remains.
